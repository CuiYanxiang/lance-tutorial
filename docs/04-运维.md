## 4.1 先认清两种「布局劣化」

长期写入后性能掉，九成是这两种：



1. **碎片（小片段过多）**：高频小 `append` 会产生大量小 fragment，扫描时打开文件次数暴涨。

2. **删除累积**：`delete` 是软删，扫描时要跳过被标删的行；删得多了扫描变慢。

解决手段就两个：**压实（compact）** 和 **清理旧版本（cleanup）**。

## 4.2 压实 compact\_files：把小片段合并、顺带物理清删



```
import lance
ds = lance.dataset("./alice.lance")

ds.optimize.compact_files(
    target_rows_per_fragment=1024 * 1024,   # 大于该行数的片段跳过，其余合并
    data_storage_version="2.2",              # 顺带把重写文件升到 2.2
)
```

要点：



* 合并按 fragment id 进行，**保留数据固有顺序**。

* 重写后的片段**不再带 deletion 文件**—— 软删行被物理抹去，扫描提速。

* **压实会让被重写片段上的旧 ANN 索引失效**（行地址变了）。所以标准顺序是：**先 compact，再重建索引**。

* 压实本身也产生新版本，**不删旧文件**（旧版本还引用着）。

**触发时机建议**：小片段数量或写频率到达阈值时跑（见 4.5 的自动策略），不要每次写都跑。

## 4.3 清理旧版本 cleanup\_old\_versions：回收只增不减的磁盘

Lance 不可变，每次写都留旧文件。旧版本有价值（快照隔离 + time travel），但不能无限留。



```
from datetime import timedelta
ds.cleanup_old_versions()                              # 默认清理 7 天前的版本
ds.cleanup_old_versions(older_than=timedelta(days=1))   # 只留最近 1 天
```

行为与红线：



* 默认只删 **Lance 能验证确实无引用** 的文件（旧版本引用过、新版本不再引用）。

* **永远不动当前活跃版本**；`older_than=timedelta(0)` 安全（只留当前版）。

* **打了 tag 的版本豁免清理**；分支引用的文件也不会被删。要彻底回收，先 `tags.delete()` / `branches.delete()`。

* ⚠️ 清理后这些旧版本**无法再 time travel**，`older_than` 按你的回滚窗口需求定。

* ⚠️ `delete_unverified=True` 会连「无法验证」的孤儿文件（失败 / 中止的提交残留）一起删 ——**只在确认没有跑超过&#x20;**`older_than`**&#x20;时长的并发操作时用**。`delete_unverified=True` + `older_than=timedelta(0)` 是**极端危险**操作，可能把正在写的文件删掉导致数据集损坏。

## 4.4 自动清理：写路径内 vs 后台定时

**写路径内自动清理**（随提交触发）：



```
from lance.dataset import AutoCleanupConfig
ds = lance.write_dataset(
    table, "./my.lance",
    auto_cleanup_options=AutoCleanupConfig(interval=20, older_than_seconds=3600),
)
# 或对已有表开启/关闭
ds.optimize.enable_auto_cleanup(AutoCleanupConfig(interval=20, older_than_seconds=3600))
ds.optimize.disable_auto_cleanup()
```



* `interval`：每 N 次提交跑一次清理；`older_than_seconds`：删除多久以前的版本。

* 配置项也可直写：`ds.update_config({"lance.auto_cleanup.interval":"20", "lance.auto_cleanup.older_than":"3600s"})`。

* ⚠️ 自动清理跑在提交路径上。**writer 没有 delete 权限、或写延迟极敏感时**，给单次写传 `skip_auto_cleanup=True` 跳过。

**推荐：后台定时清理**（高并发生产更稳）—— 把 `cleanup_old_versions` 放 cron / Airflow 定时任务，**完全移出写路径**，不影响写延迟。代价是要额外维护调度。

> 生产默认组合：
>
> **后台每天 compact 一次 + 每天 cleanup（保留窗口按业务 RPO，如 3~7 天）**
>
> ；高频小写再考虑写路径自动清理兜底。

## 4.5 并发与 MVCC：谁在同时写会怎样



* **读 ↔ 写**：快照隔离。读进程打开时锁定某个 manifest，新写不影响它。

* **写 ↔ 写**：manifest 乐观并发。两个写同时提交，后提交者会因版本冲突失败，**必须捕获并重试**。

* **混版本读写**：一旦某次提交写入了与 dataset 默认 `data_storage_version` 不同的文件，提交会自动设置配套的 reader/writer feature flag。**老客户端不认识这些 flag 会拒绝读该 snapshot**。升级纪律：

1. 先把**所有 reader/writer** 升级到混版本感知的发行版；

2. drain / 重启 /fencing 掉还在用老版本打开 dataset 的 writer；

3. 再开始写混版本文件。

* 历史上清一色的旧数据集，老客户端照样能读（feature flag 只在混版本后才需要）。

## 4.6 对象存储（S3/GS）运维要点



* **权限**：写路径若要自动清理，writer 角色必须有对象存储 **delete 权限**；只读 reader 不需要。

* **生命周期**：Lance 不替你管底层对象。对冷数据 / 老 blob 可配 S3 生命周期转低频 / 归档，但**别把当前版本引用的文件归档**—— 会导致读失败。

* **多 base / 冷热分离**：历史分区可放便宜 bucket，建表时通过 `initial_bases` 注册，查询自动跨 base 寻址。

* **监控磁盘增长**：每次写都 +1 版本，存储增长是预期内的；**暴涨异常**通常 = 开了高频写却从不 cleanup。看 `_versions/` 数量和 data 目录体积趋势。

## 4.7 回滚与灾备



* **time travel 回滚**：误写后 `ds.checkout_version(n)` 读旧快照核对，必要时把业务切回旧版；或用 tag 固定的基线版本恢复。

* **备份**：Lance 数据集就是一个目录（对象上就是一批 key）。整目录 / 整 bucket 前缀复制即备份；关键版本打 tag 后长期保留。

* **不要做**：手动删 `.lance` 目录里的数据文件 —— 必须走 `cleanup_old_versions`，否则会弄坏被版本引用的数据。

## 4.8 排障速查表



| 现象                         | 最可能原因                    | 处理                                            |
| -------------------------- | ------------------------ | --------------------------------------------- |
| 改完代码读不到新数据                 | 同一个 `ds` 对象未刷新           | 重新 `lance.dataset(path)` 打开                   |
| 磁盘随每次写暴涨                   | 从不 cleanup 旧版本           | 配后台 `cleanup_old_versions`                    |
| 删除后查询变慢                    | 软删行累积未压实                 | `compact_files`（之后重建索引）                       |
| 小片段太多、扫描变慢                 | 高频小 append               | `compact_files(target_rows_per_fragment=...)` |
| 向量查询突然不准 / 索引失效            | compact 重写了片段使旧索引失效      | compact 后 `create_index` 重建                   |
| 写提交偶发失败                    | 多写并发 manifest 冲突         | 捕获冲突、重试该写事务                                   |
| 老客户端读不到新 snapshot          | 写入了混版本文件、feature flag 不认 | 升级全部 reader/writer，fencing 老 writer           |
| `delete_unverified` 后数据集损坏 | 误删了正在进行中的写文件             | 只用确认无并发长任务时开；生产优先后台 cleanup                   |
| S3 上清理报权限错                 | writer 缺 delete 权限       | 给角色加 s3:DeleteObject（或改后台清理）                  |

## 4.9 生产上线 Checklist

* [ ] 明确并固化版本保留窗口（RPO），配后台 `cleanup_old_versions`

* [ ] 高频小写场景配 `compact_files` 定时任务，且**压实后重建 ANN 索引**

* [ ] 写并发处加冲突重试

* [ ] 关键训练 / 发布基线已 `tags.create` 固定（自动清理不会回收）
